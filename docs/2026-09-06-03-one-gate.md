# Plan — one gate: the GUI declares, the server decides

Reconciled 2026-09-07: **foundation implemented; broader proposal incomplete**.
`src/web/components/can.tsx` provides `Can` and `PlatformCan`, and
`tests/repo/action-gates.test.ts` checks action-gate usage. Presentation state
can still live in callers; API authorization remains authoritative. Reveal
mode and whole-app permission/state matrices are not implemented.
The proposal below is historical scope, not proof that every permission or
state is covered. Continue through GAP-06–08 in the
[domain register](2026-09-07-01-react-domain-coverage.md); see [current status](README.md).

## Why

The GUI is data driven. What a screen offers depends on who you are and on
the state of the thing you are looking at, and today every screen works
that out for itself, by hand. Counted 2026-09-06: 26 `can` gates across 12
files — `t.can.MANAGE_ROSTER && <ManageRoster/>` — and state checks beside
them, such as `g.can.BROADCAST_GAME && !g.isBroadcasting`. Each one is a
small private copy of a rule that lives somewhere else, and the only way to
see whether one is right is to be the right person, looking at the right
object, in the right state. Nobody can do that for all of them. The Product
Owner's words that day: "it's impossible to know if the GUI really works."

The GUI walk found one gate wrong by luck. The who-sees-what check finds
disagreements on the screens it covers. Neither makes the GUI *knowably*
right, because as long as screens decide, there is a decision on every
screen that can be wrong, and the permutations are the screens' problem.

## The change

Two moves, so that "does the GUI work for every permutation" becomes a
question with a checkable answer.

**1. The server answers every "may I", state included.** `can` today is
relations × event subtype (`allowedBy` in `src/domain/grants.ts`). It becomes
relations × subtype × the row's state: a game you may not broadcast because
somebody already is, an event you may not enter because entries have
closed, a team you may not follow because you already do (that one becomes
UNFOLLOW). One function per object type, given the row and the relations,
pure, with the state rules written once beside the grant rules. The
permutations then live where they are cheap: a unit test walks every
relation × subtype × state for each object type in milliseconds, against
the model, exhaustively — the shape `tests/worker/authz-equivalence.test.ts`
already has for relations alone.

**2. The GUI has one gate.** A single component,

    <Can action="MANAGE_ROSTER" of={team}>…</Can>

is the only way a control that performs an action reaches the screen. It
renders its children if and only if `of.can[action]`, and stamps
`data-action` on them. No screen writes `if (t.can.X)` again: the 26 gates
become 26 uses of one component, and a repo test fails any `.can.` read
outside it, the way the copy rules already fail a stray English string. A
control cannot be shown to someone the server refuses — by construction,
not by test.

With both, "the GUI is right" decomposes into four facts, each checkable
without a browser or with one small one:

- the server's `can` is right — the exhaustive unit test;
- every action the model grants has a gate on some screen —
  `tests/repo/actions.test.ts`, reading `<Can action=…>` from the tree
  instead of keeping a map;
- a change of person refetches every answer —
  `tests/e2e/identity-cache.spec.ts`, proven today; <!-- docs-check-ignore -->
- the chain composes on real screens — `tests/render/who-sees-what.spec.ts` <!-- docs-check-ignore -->
  as the smoke, surface by surface.

**3. Reveal mode, for a person.** With a toggle in the tweaks
(`TWEAK_DEFAULTS` in `src/web/index.html`, dev only), `<Can>` renders a
refused control greyed out with its reason — "needs HEAD_COACH on this
team" — instead of nothing. Walking the GUI as a visitor then shows every
control that exists and why it is hidden, which is the thing the Product
Owner cannot see today. `bun run shots` takes one walk with it on, so the
pictures show all of it too.

## What is not certain

Asked "are you sure?" on 2026-09-07. Not about all of it.

- **Sure:** the gate plus the repo test make "never shown when refused"
  hold by construction; the exhaustive test over a pure `can` is cheap and
  complete. Neither is in doubt.
- **The line between permission and presentation.** "Already following, so
  Unfollow" is about the reader and is the server's. "Nobody is
  broadcasting, so no Watch link" is about the world, and putting it in
  `can` couples the API to one screen's choices. "Permission-like state"
  is a judgement, made per case in the inventory step. Do one object type
  end to end first — games — before the rest.
- **Missing controls are not caught by construction.** The gate stops
  wrong showing. A control never written, or gated on the wrong screen,
  shows only in the tree test and in who-sees-what, which covers the
  surfaces it lists. That is sampling.
- **Fresh answers.** A `can` that depends on state is stale the moment the
  state changes elsewhere, until the row refetches. Live pages poll; others
  do not. The identity-cache bug of 2026-09-06, in a different coat.
- **Cost.** Twenty-six gates is a day. The server half changes the `can`
  contract and the equivalence tests with it, and its payoff is believed,
  not measured. That is another reason to do games first and look.
- Of the four facts under "The change", two need no browser (the server
  test, the tree test); the render smoke and the identity test do.

## Rules

- A control performs one model action, and says which.
- No `.can.` read and no `useCan(` outside the gate. No rule about
  permission or permission-like state in the GUI.
- The server's answer is the only answer. The GUI never reasons about who
  the reader is or what the row's state allows; it renders what it is told.
- The gate is the same in production and dev; reveal only changes what a
  refusal looks like.

## Original proposed steps (not a live checklist)

- **The gate.** `src/web/components/can.tsx` <!-- docs-check-ignore -->: `<Can action of>` for
      per-row actions and `<Can action>` for platform ones (`useCan`), one
      component, `data-action` stamped, reveal mode read from the tweaks.
- **Move the 26 gates.** Each `x.can.ACTION && <…>` becomes
      `<Can action="ACTION" of={x}>`. The three `data-action` attributes
      stamped by hand for the first who-sees-what slice go, because the
      gate stamps them.
- **The repo test.** No `.can.` member read and no `useCan(` outside
      can.tsx — an oxc walk over `src/web`, the same runner as the copy and
      import rules, with the reason beside it.
- **State into the server.** Inventory every state check that sits
      beside a gate (five found on 2026-09-06: broadcasting, following, and
      the entry, registration and result states), move each into the
      object's `can` with the row as input, delete it from the GUI. The
      exhaustive unit test per object type: relation × subtype × state,
      against the model.
- **Actions read the tree.** `tests/repo/actions.test.ts` derives
      action → screen from `<Can action=…>` uses, and checks the `@answers`
      annotations agree until they are deleted.
- **Reveal mode.** The tweak, the greyed rendering with the reason, and
      one `bun run shots` walk with it on.
- **The smoke, everywhere.** who-sees-what covers every surface in the
      shots list, using the gate's `data-action` rather than hand stamps.

## Done when

No `.can.` outside the gate; every rule about what a reader may do lives
on the server with an exhaustive test; a visitor with reveal on sees every
control and its reason; who-sees-what is green on every surface.
