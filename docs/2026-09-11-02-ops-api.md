# Task — `ops api`: one executor over the router, for humans and for help-tools

**File:** `2026-09-11-02-ops-api.md` — refer to this plan by that name.

**Repo:** `joeblew999/remy-sport`
**Follows:** `docs/done/2026-09-11-01-unify-server-routing-orpc.md` (absorbs its F5 follow-up).
**Precedes:** notifications unification (which will use `ops api` to debug the DO scheduler).
**Scope:** one PR, small. No schema change, no new auth, no deploy risk beyond `sites/help-tools`.

## What this gets us

1. **Call any procedure from the terminal, typed, on any environment.** `bun run ops api call events.list --env staging` prints JSON. `--input` is validated against the real schema before anything is sent, so a mistake is a local error naming the field, not a 400 to decode. Today the only ways are the browser or hand-written `curl`.
2. **The notifications work becomes debuggable.** It adds a Durable Object per fixture with alarms. When one does not fire, the question is "what is this DO's state" and "enqueue one reminder for this game now" — with `ops api` that is one command, not a throwaway script each time.
3. **The last hand-written description of the API goes away.** `help-tools`' six agent-callable operations are a list in a `.mjs` file that agrees with the router by inspection. After this they are the six procedures tagged `agent`, and a test proves it is exactly six. Adding an operation an agent may call becomes adding a tag. This is the foundation of the AI surface, not a prototype beside it.

What it does **not** get us yet: a CLI or client for outside developers. That needs API keys, and nothing issues keys today — Part D names it as the issue after this one.

## Principle

**There is one way to call a procedure from outside the app, and it is derived from the router.** `ops api` is that executor for a person at a terminal; `help-tools`' assistant surface is the same executor behind a tag filter and an MCP transport. Neither carries a list of operations.

## Current state

| Thing | Where | Problem |
|---|---|---|
| Typed client | `src/api-client.ts` — `createApiClient(baseUrl, { headers })` over `OpenAPILink` | works; only reachable from scripts that import it |

| `ApiKey` scheme | declared in `src/api/openapi.ts` | nothing issues keys; `authed` procedures are cookie-session only |

## Part A — `ops api`

### A1. Verbs

```
bun run ops api list [--env X] [--internal]
bun run ops api call <router.key> [--input <json>] [--env X] [--yes]
bun run ops api schema <router.key>
```

- **`list`** — every procedure the environment publishes: key, method + path, audience (`public` / `infrastructure` / `dev:<capability>`), one-line summary from `.route({ summary })`. Source: `generate(audience)`, filtered by `excludeInternal(env)` for the target — the same predicate the deployment uses, so `list --env production` shows exactly what production serves.
- **`call`** — walks the router by key (`events.list`, `dev.seed`), parses `--input` as JSON (or `{}`), validates it **locally** against the procedure's input schema before any request leaves the machine (a bad input is a local error with the field name, not a 400), then calls through `createApiClient(originOf(env))`. Output is the response as JSON on stdout; an `ORPCError` prints `code` and `message` to stderr and exits non-zero. `NOT_FOUND` on a dev-gated procedure prints "not mounted on <env> (POLICY[env].<capability>)" — the seam the previous PR named.
- **`schema`** — the procedure's input and output JSON Schema, from the generator, for composing `--input`.

### A2. Environment and safety

- `--env` resolves through `scripts/lib/cloudflare.ts` like every other verb; `dev` is the local Worker.
- `call` on **production** with a procedure whose method is not `GET` requires `--yes`, printed as: "POST events.create on production — pass --yes." Same shape as `provision --apply`.
- `authed` procedures need a session. Until keys exist (Part D, deferred), `call` accepts `--cookie <value>` for a session cookie copied from the browser, and says so in `--help`. It never stores it.
- Everything goes through `createApiClient`; the repo test from the previous PR (no raw `fetch` of `/api/` in `scripts/`) keeps `ops api` honest.

### A3. Tests

- `tests/repo/ops-api.test.ts`: every router key is callable by name — walk the router, assert `resolveProcedure(key)` returns it, and that `schema <key>` produces valid JSON Schema for each. A renamed key fails here before anyone runs it.
- `tests/unit/ops-api-input.test.ts`: `call` refuses a bad `--input` locally with the field name and makes no request (assert the fetch mock is not called).
- `tests/worker/ops-api.test.ts`: `call health.versions` against the pool returns the placeholder stamp; `call dev.seed` returns `NOT_FOUND` with the "not mounted" message when the pool's `POLICY` withholds it.

## Part B — `help-tools` derives its operations from the router

### B1. The `agent` tag

Add `agent` as a policy-mark field alongside `capability`: `pub.agent()` (or `.meta({ agent: true })` — whichever fits the existing `marked()` shape) on exactly the six read-only procedures `help-tools` exposes today: `events.list`, `events.get`, `teams.list`, `teams.get`, `games.list`, `games.get`. The generator gains `generate("agent")`: the public audience further filtered to `agent`-marked procedures. Domain tags as before.

### B2. `application.mjs` reads the generated spec

Replace `operations = ['events','teams','games'].flatMap(...)` with a load of `generate("agent")`'s output — either at `help-tools` build time (preferred: it's a Worker deployed from this repo by `ops docs-release`, so the build can import the generator) or fetched from `${appOrigin}/api/openapi.json` and filtered by the `agent` tag at startup, with the existing `contract()` cache. Build-time is one source; fetch-time is one source plus a network dependency. **Build-time.**

`declarations()` (Gemini function declarations) and the MCP tool registrations in `docs-server.mjs` derive from the same loaded set. No `flatMap`, no resource list, no hand-written names.

### B3. `worker-check.mjs` becomes the contract test for the tag

Keep its three assertions — 6 paths, all `get`, `servers[0].url` — unchanged in meaning. They now test that the `agent` tag is on exactly six procedures and that all six are reads. Add a fourth: no `agent`-tagged procedure is `authed` or `infrastructure` (the surface stays public and credential-free, which `application.mjs`'s header promises).

### B4. Executor, not a second client

`help-tools` calls the app through `createApiClient` (or, if the `.mjs` boundary makes importing the TS client awkward, a generated JS build of it — not a hand-written `fetch` wrapper). `application.mjs`' `apiOrigin()` guard (HTTPS or loopback, no credentials, no path) stays as the boundary check in front of it.

## Part D — Deferred, named

- **API key issuance.** The `ApiKey` scheme is declared; nothing mints keys. A `keys.create / keys.revoke` procedure pair, a settings page, and `ops api call --key` come together as their own issue, and are the prerequisite for a published `@remy-sport/api` client and `remy` CLI. Not here.
- **`@remy-sport/api` + `remy` CLI for external developers.** oRPC's "Publish Client to NPM" recipe over the public contract; `ops api` with the internal verbs stripped. After keys, after the contract has settled through the next two migrations.

## Constraints

- No new runtime dependencies in the app Worker. `help-tools` may gain a build step importing the generator; it gains no runtime dependency on app source (its README's promise).
- `ops api call` never stores a cookie or key.
- The `agent` tag is a policy-mark field, never parsed from `why`.
- `worker-check.mjs`'s existing assertions keep their meaning.

## Delivery order

1. `ops api list` and `schema` from the generator — read-only, no network.
2. `ops api call` with local validation, `--yes` on production, `--cookie`; the three tests.
3. `agent` mark on the six; `generate("agent")`; repo test that exactly six carry it.
4. `application.mjs` loads the generated set at build time; `declarations()` and MCP registrations derive from it; `worker-check.mjs` gains the fourth assertion.
5. `ops docs check`, `ops docs-release` to the tools origin, `ops smoke` on both app environments (unchanged surface, but the check proves nothing moved).

## Decisions (made, Sep 2026)

- One executor over the router for CLI and assistant surface; neither keeps a list.
- `agent` is a policy-mark field; the six read-only procedures carry it; `worker-check.mjs` is the test that it is exactly six.
- `help-tools` derives at build time, not by fetching at startup.
- Production `call` on non-GET requires `--yes`.
- Keys and the external client are deferred to their own issue.
